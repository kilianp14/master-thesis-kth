\section{Adaptive Fast Mode Switching}
The core of the proposed system lies in its ability to dynamically transition between operating modes (Regular Paxos and Fast Paxos) based on real-time conditions. Whenever a node attempts to append a proposal to the replicated log, it collects data representing the current environment and evaluates through an internal predictor if choosing the fast-path for this entry is sensible. This design aims to allow the system to react quickly to shifts in proposal rates or network conditions.

With nodes being able to select modes independently, we enable the system to handle heterogeneous workloads where some nodes may be more prone to contention than others in a more effective manner. In comparison to a design with global synchronization regarding the current Paxos variant, different servers in the consensus cluster can have varying operating modes, requiring additional logic for ensuring safety as discussed in Section \ref{sect:mode-interoperability} and Section \ref{sect:quorum-logic}.

While followers can utilize the adaptive predictor to decide between forwarding a proposal (Regular Paxos) or attempting a fast-path (Fast Paxos), the leader should consistently operate in the regular mode for two reasons: A standard majority quorum is easier to achieve than the larger fast quorum and the leader does not incur the forwarding penalty, which is the main drawback of using the regular mode over the fast mode.

\subsection{Mode Interoperability}
\label{sect:mode-interoperability}
The coexistence of multiple operating modes for the same slot within a single ballot necessitates a robust mechanism for ensuring that nodes can process messages from different protocol variants without compromising safety or consistency. To achieve this interoperability, every \texttt{Accept} and \texttt{Accepted} message is tagged with a corresponding \texttt{AcceptStatus}:
\begin{itemize}
\item \textbf{LeaderAccept (Regular path):} Indicates a proposal issued by the leader via the standard Paxos protocol.
\item \textbf{FastAccept (Fast path):} Indicates a proposal initiated directly by a follower attempting to reach a fast quorum.
\item \textbf{SlowAccept (Slow path):} Indicates a remedial proposal issued by the leader to resolve a detected collision of proposals.
\end{itemize}

Append handling depends on the node’s local mode selection. In \textit{Fast Paxos} mode, the node broadcasts a \texttt{Accept} message with the \texttt{FastAccept} status directly to peers after assigning the slot with the smallest index that is still empty to the proposal. In \textit{Regular Paxos} mode, the proposal is forwarded to the current leader, which assigns the slot and broadcasts an \texttt{Accept} message with the \texttt{LeaderAccept} status.

A challenge in decentralized mode switching is a collision, where multiple nodes attempt to occupy the same log slot with different values via the fast path or the regular path. To maintain liveness, the leader maintains a record of all \texttt{Accepted} messages received from the cluster for every open slot. If the leader detects that no proposal can be decided on due to a lack of responses or conflicting values for the same index, it triggers a resolution via the slow path. The concrete logic for the collision detection is described in Section \ref{sect:quorum-logic}. When having to use the slow path, the leader determines the correct proposal to choose for this slot and broadcasts a new \texttt{Accept} message with the \texttt{SlowAccept} status.

The safety of the replicated log relies on strict rules regarding when a node is allowed to update its local state. In this system, followers apply logic that respects the "authority" of the message status. \texttt{FastAccept} and \texttt{LeaderAccept} messages are treated as first-come, first-served. A follower is only allowed to accept these values if the corresponding slot in its local log is currently empty. This prevents an uncoordinated follower from inadvertently overwriting a value that might have already achieved a quorum elsewhere. In contrast, a message with \texttt{SlowAccept} status is treated as a command to resolve a conflict. Since this status is only issued by the leader after observing the cluster state, it is permitted to override any previously accepted value in a follower’s log. Under the assumption of a stable leader and quorum connectivity, this hierarchy is intended to allow the leader to converge conflicting proposals toward a single value.

\subsection{Quorum Logic and Collision Detection}
\label{sect:quorum-logic}
This section details the deterministic logic utilized by the cluster leader to evaluate quorums, detect proposal collisions, and drive individual log slots to a decided state. None of the additional state maintained by the leader requires persistence to stable storage for recovery purposes even in a fail-recovery model.

The presented mechanisms assume a phase where the leader is in a stable accept phase. While handling leader failures or leader changes and executing the subsequent log synchronization are critical components for a thought-out consensus protocol, the more complex mechanisms required are considered out of scope for this specific analysis due to its experimental nature.

\begin{algorithm}[t]
\caption{Quorum Evaluation and Collision Resolution}
\label{alg:quorum_eval_collision_resolution}

\begin{algorithmic}[1]
\Procedure{ComputeProposeResult}{$proposals$}
\If{\textbf{not } majority quorum on $|proposals|$}
    \State \Return $\textsc{Pending}$
\EndIf
\State $(e^\star, leader, fast, slow) \gets$ entry in $proposals$ with maximum total votes
\If{majority quorum on $leader$ \textbf{or } \Statex \qquad\: fast quorum on $fast$ \textbf{or } \Statex \qquad\: majority quorum on $slow$}
    \State \Return $\textsc{Chosen}(e^\star)$
\EndIf
\If{\textbf{not } fast quorum on $|proposals|$}
    \State \Return $\textsc{Pending}$
\EndIf

\State $remaining \gets |nodes| - |proposals|$
\For{\textbf{each} $(e, leader, fast, slow)$ \textbf{in} vote counts of $proposals$}
    \If{fast quorum on remaining + fast \textbf{or } \Statex \qquad\qquad majority quorum on remaining + leader \textbf{or } \Statex \qquad\qquad slow > 0}
        \State \Return $\textsc{Collision}(e)$
    \EndIf
\EndFor
\State \Return $\textsc{Collision}(e^\star)$
\EndProcedure
\end{algorithmic}
\end{algorithm}

To evaluate the current state of an uncommitted log entry, the leader leverages Algorithm \ref{alg:quorum_eval_collision_resolution}. This algorithm operates as a pure function that takes the set of collected proposals and votes for a given slot and returns its discrete operational status: $\textsc{Pending}$, $\textsc{Collision}(entry)$ with $entry$ being a save value to execute a slow-path with or $\textsc{Chosen}(entry, acceptStatus)$ where the $entry$ was chosen via the path indicated by the $acceptStatus$.

The evaluation begins by checking for immediate quorum satisfaction. A value is chosen once it reaches the quorum required by its \texttt{AcceptStatus}. This requires a standard majority quorum for entries tagged with $\textsc{LeaderAccept}$ or $\textsc{SlowAccept}$, and a larger fast quorum for entries tagged with $\textsc{FastAccept}$. Because all these ways of acceptance require at least a majority of votes, it is enough to check the entry with the maximum total votes. Additionally, if less than a majority has voted, this also means that no decision could have been reached, making the slot $\textsc{Pending}$.

If no single entry has achieved its required quorum, the leader must determine whether a collision has occurred and select a value that cannot conflict with a potentially chosen value for the slow path. Merely collecting a simple majority of total cluster responses is insufficient to safely trigger collision resolution in this mixed mode environment. Consider, for instance, a cluster of five nodes, where a regular majority quorum consists of three and a fast quorum of four nodes. If the leader received three responses for a slot with one being a $\textsc{LeaderAccept}$ for value $A$ and two $\textsc{FastAccept}$ messages for value $B$, the outcome remains ambiguous, although a simple majority of responses has been gathered. With 2 nodes yet to respond, value $A$ could still theoretically achieve a majority quorum, while value $B$ could concurrently reach a fast quorum. Initiating a slow-path recovery at this stage risks overriding a value that might have achieved a quorum elsewhere in the network.

To avoid overriding a value that may still reach quorum, the leader must wait until a fast quorum of total responses has been collected for the slot. Once a fast quorum of responses is observed, it becomes mathematically impossible for more than one value to be able to reach its respective quorum using the remaining uncast votes. A proof of this is written out in Appendix \ref{seca:slow_path_resolution_safety_proof}.

After this threshold is met, the leader executes the final loop of Algorithm \ref{alg:quorum_eval_collision_resolution} to identify a valid candidate for the slow path. The leader computes the number of uncast votes ($remaining$) and checks if any entry can still mathematically achieve its required threshold. If an entry retains the potential to reach its quorum, it is selected as the safe value for the slow path. In cases where high contention prevents any entry from being able to reach a quorum, the system falls back to the entry with the highest current vote count.

\begin{algorithm}[t]
\caption{Leader Proposal Processing}
\label{alg:leader_proposal}

\begin{algorithmic}[1]

\Procedure{AddNewProposal}
{$pid, slotIdx, entry, status$}

\If{$slotIdx < decidedIdx$}
    \State \Return $\textsc{NoAction}$
\EndIf

\State Append $(pid, entry, status)$ to $\textit{acceptMeta}[slotIdx]$
\State $previous \gets \textit{slotResults}[slotIdx]$
\State $result \gets \Call{ComputeProposeResult}{acceptMeta[slotIdx]}$
\State $\textit{slotResults}[slotIdx] \gets result$

\If{$result = \textsc{Chosen}(\_)$ and $slotIdx = decidedIdx$}

    \State $newDecidedSuffix \gets [\ ]$

    \While{$\textit{slotResults}[decidedIdx] = \textsc{Chosen}(e)$}
        \State Append $(decidedIdx,e)$ to $newDecidedSuffix$
        \State Remove $\textit{slotResults}[decidedIdx]$
        \State Remove $\textit{acceptMeta}[decidedIdx]$
        \State $decidedIdx \gets decidedIdx+1$

    \EndWhile

    \State \Return $\textsc{DecidedAction}(newDecidedSuffix,decidedIdx)$
\ElsIf{$result = \textsc{Collision}(e)$ and $previous = \textsc{Pending}$}
    \State \Return $\textsc{SlowPathAction}(slotIdx,e)$
\Else
    \State \Return $\textsc{NoAction}$
\EndIf

\EndProcedure

\end{algorithmic}
\end{algorithm}

To translate the described quorum evaluation into concrete leader actions, the leader executes Algorithm \ref{alg:leader_proposal} upon receiving any accepted proposal, whether initiated by a follower or by itself. This mechanism serves as a stateful wrapper around the functional quorum computation.

The procedure begins with an initial safeguard step: any proposal targeting a log index prior to the currently contiguous decided sequence (denoted as $decidedIdx$) is immediately discarded as obsolete. Valid proposals are subsequently added to the internal metadata for the corresponding slot, ensuring an up-to-date record of all cast votes. The algorithm then invokes \texttt{ComputeProposeResult} and maps its returned state to one of three specific leader actions:
\begin{itemize}
    \item \textsc{DecidedAction}: This action is triggered when the slot achieves a \textsc{Chosen} state and perfectly aligns with the current $decidedIdx$. Upon this trigger, the algorithm sweeps forward through the internal metadata to identify all consecutively chosen slots. These contiguous entries form a single suffix that can now be permanently decided, subsequently advancing the cluster's $decidedIdx$.
    \item \textsc{SlowPathAction}: If the evaluation transitions the slot's state from \textsc{Pending} to $\textsc{Collision}(e)$, the leader emits a \textsc{SlowPathAction}. This directive instructs the leader to broadcast an \texttt{Accept} message with the \texttt{SlowAccept} status for value $e$, thereby resolving the detected collision according to the hierarchical rules established in Section \ref{sect:mode-interoperability}.
    \item \textsc{NoAction}: This fallback is returned either when the slot remains in a \textsc{Pending} state due to insufficient votes, or when a collision has already been detected and acted upon in a previous iteration. The latter condition is required to prevent the emission of duplicate slow-path broadcasts for the same log index.
\end{itemize}

Assuming a stable leader and continued fast-quorum connectivity, the design guarantees liveness during the accept phase. Compared to regular Sequence Paxos, if the cluster degrades to a simple majority, the leader might not be able to safely resolve collisions, effectively halting the log.

\section{Heuristic Score for Fast-Path Success}
While the leader-side proposal processing and collision resolution described previously provides safety and liveness under favorable conditions, the followers must individually choose the operating modes to use to achieve optimal latency for each request. Compared to regular Sequence Paxos, this means choosing to use the fast-path when it is likely successful, avoiding the message delay for forwarding the request. Compared to Fast Sequence Paxos, this means choosing the safer forwarding option when a fast-path attempt is considered risky, since a collision  and its subsequent slow-path resolution and potential need for retrying introduce heavy latency penalties.

From the perspective of a follower, we can consider a fast-path attempt successful only if its proposal achieves a fast quorum directly, without requiring a slow-path collision resolution. Conversely, a failure occurs whenever this optimal path is interrupted. A fast-path attempt will fail if the target slot is claimed by a concurrent proposal by the leader through the regular path (majority quorum of $\textsc{LeaderAccept}$ messages), claimed by a different follower's concurrent fast-path proposal (fast quorum of $\textsc{FastAccept}$ messages), or stalled entirely by a collision that forces the cluster into a slow-path recovery.

To dynamically find out the right mode to use, we design a heuristic that condenses real-time metrics into a score estimating the probability of a fast-path succeeding to serve as the foundation for the mode predictor. For this purpose, we simulate lots of distributed consensus networks to analyze how network latency and proposal rates affect a follower node's ability to successfully commit a proposal via a fast quorum path versus experiencing collisions or overwrites.

\subsection{Important Metrics}
To isolate the environmental variables that potentially impact fast-path outcomes, we define a set of system features tracked from the perspective of an individual follower. These metrics can be put into three categories:

\vspace{1em}
\noindent\textbf{Network Latency:}
\begin{itemize}
    \item \textit{Latency to Leader}: Baseline message delay to the designated leader.
    \item \textit{Latency to Majority Quorum}: The time required until a majority quorum can be reached with a message.
    \item \textit{Latency to Fast Quorum}: The time required until a fast quorum can be reached with a message.
    \item \textit{Maximum Latency}: Baseline message delay to the furthest node .
\end{itemize}

\noindent\textbf{Traffic and Proposal Rates:}
\begin{itemize}
    \item \textit{Leader Proposals/sec}: Volume of concurrent accept requests initiated by the leader. This is a measure about how many other requests take the regular path.
    \item \textit{Own Proposals/sec}: The individual request rate of the follower.
    \item \textit{Other Followers' Proposals/sec}: The aggregate concurrent request rate originating from all other followers. This is a measure about how many other requests take the fast path.
    \item \textit{Max Follower Proposals/sec}: The peak request rate observed from a competing follower.
\end{itemize}

\noindent\textbf{System Scale:}
\begin{itemize}
    \item \textit{Node Count}: Total number of active nodes operating within the  cluster.
\end{itemize}

To determine which of these metrics actually drive the system's behavior, we performed a feature importance analysis on the collected simulation data. An XGBoost regression model~\cite{Chen-XGBoost-2016} was trained using the established features to predict the follower's fast-path success rate. To ensure the feature set comprehensively captured the system dynamics before analyzing importance, the model was evaluated against a holdout test dataset. The model achieved a low \gls{RMSE} of $0.00372$ and a high \textit{Coefficient of Determination} ($R^2 = 0.97458$). This $R^2$ score indicates that the selected metrics account for approximately 97.5\% of the variance in fast-path success, validating that the input features successfully capture the underlying mechanics of the system.

With the model validated, the relative impact of each metric was quantified using the \textit{Information Gain} of the underlying decision trees, which measures the total reduction in prediction uncertainty contributed by a specific feature across the entire ensemble. This result is illustrated in Figure~\ref{fig:all-features-importance}.

To minimize system overhead, the resulting score function, however, should be simpler and efficient to compute, requiring as little runtime metric tracking as possible. For this purpose, the goal is to first reduce the feature space without losing much performance. From the original feature importance plot, we can see that the latency to a fast quorum is by far the most important network latency metric. If we remove all other latency features and repeat the XGBoost training procedure, we achieve a \gls{RMSE} of $0.00631$ and and $R^2$ score of $0.95689$, which demonstrates that the model retains most of its predictive accuracy despite using a significantly smaller feature set. Figure~\ref{fig:one-latency-features-importance} shows the resulting feature importance.

With these three metrics, we now try to build a score function predicting the likelihood of fast-path success that is easy to evaluate.


\subsection{Score Function}
To explore how the three remaining metrics interact, we can look at the time a proposal spends in flight. The \textit{Latency to Fast Quorum} can be thought of as a window where a fast-path proposal is vulnerable to competition. During this time, requests from both the leader and other followers could potentially disrupt the fast path. Therefore, summing these two rates and multiplying by the latency gives a dimensionless value that could intuitively track the number of competing proposals issued during that window. This combination provides a plausible starting point for a well-defined score function, which is also underlined by the fact that an XGBoost model just on this metric produces a \gls{RMSE} of $0.00806$ an $R^2$ score of $0.94495$. This is very close to the results achieved using the original features separately.

When visualizing the "competing proposals" against the fast-path success rate in log-space (as done in Figure~\ref{fig:score-function}), a clear pattern emerges. The data exhibits a distinct sigmoid-like shape, with the success rate remaining near one for low values, before dropping sharply, and flattening out at zero. 
\begin{figure*}[t]
    \includegraphics[width=\linewidth]{figures/score_function.pdf}
    \caption{Observed fast-path success rate versus the expected number of competing proposals. The red line highlights the analytical heuristic score used for prediction.}
    \label{fig:score-function}
\end{figure*}

To approximate this relationship, we fit a sigmoid function using the "competing propoals", $x$, which is the product of the fast quorum latency and the combined proposal rate. The model is formulated as:
$$S(x) = \frac{1}{1 + e^{k(\ln(x) - \ln(x_0))}}$$
A curve fit yields a steepness factor of around $k \approx \frac{5}{4}$ and a parameter $x_0 \approx 0.5$, which marks the inflection point where the predicted success rate drops to $0.5$. The value of the later makes intuitive sense, as when there is a $50\%$ chance of a competing proposal, then it is imaginable that there is roughly a $50\%$ chance of our fast-path attempt not being involved in a conflict.

Inserting these values and transforming the equation leads to the final heuristic score function, as visualized in Figure \ref{fig:score-function}, in the following form:
$$\vec{x} = \begin{bmatrix} x_1 \\ x_2 \end{bmatrix} = \begin{bmatrix} \text{Fast Quorum Latency (s)} \\ \text{Incoming Accept Messages/s} \end{bmatrix}$$
$$S(\vec{x}) = \frac{1}{1 + (2 \cdot x_1 \cdot x_2)^{\frac{5}{4}}}$$

With this score function, we achieve a \gls{RMSE} of $0.00817$ and an $R^2$ score of $0.94422$ on the test data. A summary comparing the performance metrics of each model iteration against the original feature set is provided in Table~\ref{tab:model-performance-comparison}. The function can now serve as the heuristic notion of uncertainty, as needed for \gls{CRC}, around the mode prediction.

\section{Risk-Controlled Mode Prediction}
To bound the risk of failed fast-path attempts, the system incorporates the heuristic function into a risk-controlled prediction layer, outlined in this section. This framework wraps the scoring model to guarantee that the rate of fast-path failures remains below a user-specified significance level $\alpha$. This failure rate is measured relative to the total number of append attempts initiated by the node, rather than only the subset of proposals where the fast-path was actively selected.

\subsection{Risk Specification}
To formulate the mode selection as a risk-control problem, the system's outcomes and penalties must be strictly defined. We establish this formulation using three primary components: the label space, the loss function, and the user-defined risk level.

First, we define the operational label space of a proposal attempt as $\mathcal{Y} = \{\textsc{Success}, \textsc{NoSuccess}\}$. A $\textsc{Success}$ indicates that a fast-path proposal from the perspective of the proposing follower achieves a fast quorum directly under the current network conditions. Conversely, a $\textsc{NoSuccess}$ means that the attempt would fail. This could be either due to a leader proposal for the same slot that receives a majority quorum on \texttt{LeaderAccepts}, a competing follower's proposal achieving a fast quorum on \texttt{FastAccepts} for the desired slot, or general contention requiring a leader-initiated slow-path recovery.

To control the failure rate of fast-paths, which is the risk we are trying to control, we have to penalize the false positives, where a fast-path is chosen and ends up being unsuccessful. If we fall back to the conservative/regular path whenever the \texttt{NoSuccess} label is included in the prediction set, the loss can be defined as such: The loss to $1$ whenever the true outcome is \texttt{NoSuccess}, but the prediction set fails to include \texttt{NoSuccess} (meaning the system confidently, but incorrectly, predicted a fast-path success) and $0$ otherwise. This loss is mapped using Table \ref{tab:loss-matrix}.

The design does not punish conservative predictions where the fast-path would have succeeded but the system safely defaulted to the regular path. The reason for this choice is that such a punishment simply does not fit into a loss function that has to satisfy the monotonicity properties relevant to provide the guarantees of \gls{CRC}, as outlined in Section \ref{sect:conformal_risk_control}.

Finally, the framework bounds the risk using a user-specified risk level $\alpha \in (0, 1)$, which dictates the target failure rate. If we had an exchangable calibration set, the standard \gls{CRC} procedure would provide the following guarantee for a new test point:
$$\mathbb{E}(\mathcal{L}(\mathcal{C}_{\widehat\lambda}(X_{test}), Y_{test})) \le \alpha$$
Since real-life workloads are unlikely to be exchangable, however, we instead use the rolling risk-control procedure (as defined in Section \ref{sect:adaptive_conformal_inference}), which gives us the following for a stream of decision problems:
$$\lim_{T \to \infty} \frac{1}{T} \sum_{t=1}^T \mathcal{L}(\mathcal{C}_{\lambda_t}(X_t), Y_t) \le \alpha$$
Here, the converging value is bounded by $\alpha$ instead of being equal to it, as outlined previously. The reason is that in a setup where the fast-path always succeeds, the failure rate (and therefore the risk) is zero. Formally, our loss function does not satisfy the property that it has to produce a value higher than $\alpha$ when provided an empty prediction set since $\mathcal{L}(\emptyset, Success) = 0 < \alpha$.

\subsection{Decision Layer}
To execute runtime mode switching, each follower monitors local environment metrics. The fast quorum latency can be tracked continuously via a sliding window of recent message round-trip times to a fast quorum of peers, while the incoming proposal rate is calculated by recording the timestamps of arriving \texttt{Accept} messages from other nodes within a moving time window.

\begin{algorithm}[t]
    \caption{Conformal Mode Prediction}
    \label{alg:conformal_mode_prediction}
    \begin{algorithmic}[1]
        \Procedure{GetPredictionSet}{$features, \lambda$}
            \State $scores \gets \textsc{Model}(features)$
            \State $predictionSet \gets [\ ]$
            \For{\textbf{each} $(label, score)$ \textbf{in} $scores$}
                \If{$score \ge 1.0 - \lambda$}
                    \State Append $label$ to $predictionSet$
                \EndIf
            \EndFor
            \State \Return $predictionSet$
        \EndProcedure
        \vspace{0.5em}
        \Procedure{GetNewMode}{$features$}
            \State $labels \gets \Call{GetPredictionSet}{features, \widehat{\lambda}}$
            \If{$\textsc{NoSuccess} \in labels$}
                \State \Return $\textsc{RegularPaxos}$
            \Else
                \State \Return $\textsc{FastPaxos}$
            \EndIf
        \EndProcedure
    \end{algorithmic}
\end{algorithm}

For every proposal attempt, the decision layer follows Algorithm \ref{alg:conformal_prediction}. First, the tracked metrics are fed into the heuristic function to obtain probability scores for both outcomes in the label space $\mathcal{Y}$. Next, a prediction set is constructed by including any label whose assigned score satisfies the threshold condition bounded by the conformal parameter $\widehat{\lambda}$. Intuitively, a threshold of $\widehat{\lambda} = 1$ always returns the full label set, forcing a maximally conservative posture, whereas a threshold of $\widehat{\lambda} = 0$ collapses the selection down to an empty set.

Finally, the contents of the prediction set are directly translated into an operational mode for the proposal. If the set contains the \texttt{NoSuccess} label, the node falls back to Regular Paxos, forwarding the proposal to the leader. Conversely, if \texttt{NoSuccess} is absent from the prediction set, the node switches to FastPaxos mode and initiates a fast-path broadcast.

\subsection{Calibration Strategy}
\begin{itemize}
    \item \textbf{The Counterfactual Data Problem:} To calibrate the system, nodes need ground-truth data on whether a fast-path attempt would have succeeded under current network conditions.
    \item \textbf{Shadow Proposals (\texttt{TestAccept}):} To solve this, the protocol introduces a safe, parallel data-gathering mechanism. When a node is in the calibration phase and forwards a regular proposal to the leader, it simultaneously broadcasts a \texttt{TestAccept} message to all peers.
    \item \textbf{State-Safe Tracking:}
    \begin{itemize}
        \item Followers treat \texttt{TestAccept} messages passively: they acknowledge them if the target slot is empty, but they do not write them to the actual replicated log -> answers sender.
        \item If a \texttt{TestAccept} accumulates a fast quorum of votes, the original proposer records a \texttt{Success} label for those feature conditions.
        \item If the actual slot is decided by the leader before the test proposal reaches a fast quorum, the proposer records a \texttt{NoSuccess} label.
        \item Not perfect, might underestimate at times (forwarding over leader somehow faster or dropped answer) but good enough in stable network conditions
    \end{itemize}
    \item \textbf{Threshold Optimization:} Once sufficient calibration data is collected, the node computes the optimal $\hat{\lambda}$ parameter. It utilizes a binary search algorithm (running for 80 iterations over the interval $[0, 1]$) to find the exact root where the empirical risk over the calibration set is bounded by the significance level $\alpha$.
    \item Maybe include a sequence diagram illustrating a follower sending a \texttt{ProposalForward} to the leader while simultaneously broadcasting \texttt{TestAccept} messages to the cluster, demonstrating how the calibration data is gathered without altering the true log state.
\end{itemize}
