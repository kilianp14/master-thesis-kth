This chapter introduces an adaptive, decentralized architecture for fast-path routing in a replicated log abstraction layer with statistical guarantees on fast-path risk. Whenever a node attempts to append a proposal, it evaluates real-time conditions to determine the optimal operating mode (Regular Paxos or Fast Paxos) through an internal predictor. With nodes being able to select modes independently, the goal is to enable the system to handle heterogeneous workloads in a way that reduces end-to-end latency while maintaining trust through conformal guarantees.

The coexistence of multiple operating modes for the same log slot within a single ballot requires interoperability mechanisms. The underlying consensus layer must be modified to evaluate mixed-mode proposals and detect and resolve collisions without compromising the safety or liveness of replicated logs. By calibrating a dynamic selection threshold using \gls{CRC} and Rolling Risk Control, the design controls the long-term empirical rate of fast-path failures toward a user-defined target, safeguarding the system against the latency penalties of frequent slow-path recoveries.

Section \ref{sec:decentralized_mode_switching} describes consensus modifications required to evaluate mixed-mode proposals and resolve collisions. Section \ref{sec:heuristic_score} establishes a heuristic for estimating fast-path success based on real-time metrics. Finally, Section \ref{sec:risk-controlled_mode_prediction} details how this heuristic is integrated into a risk-controlled prediction layer to provide a statistical guarantee on fast-path failures.

\section{Decentralized Mode Switching}
\label{sec:decentralized_mode_switching}
To achieve a decentralized architecture where nodes evaluate operating modes independently, the consensus protocol must account for structural asymmetries within the cluster. While followers actively select between forwarding proposals (Regular Paxos) or initiating localized fast-path broadcasts (Fast Paxos), the leader consistently operates in the regular mode. This asymmetrical design stems from two practical considerations: a standard majority quorum is mathematically easier to achieve than a larger fast quorum, and the leader inherently avoids the forwarding latency penalty that represents the primary drawback of regular mode execution. Allowing individual followers to make localized decisions, however, requires specialized interoperability rules (see Section \ref{sect:mode-interoperability}) and modified leader-side tracking logic (see Section \ref{sect:quorum-logic}) to maintain consistency.

As noted previously, the purpose of the protocol modifications presented in this section is not to design a production-ready consensus algorithm. Instead, they define an experimental protocol variant that is sufficiently specified to study the feasibility and performance implications of decentralized mode switching under controlled assumptions. Consequently, several aspects required for a complete consensus protocol, including leader election, recovery after failures, persistent state, and full correctness and liveness proofs, are intentionally excluded from the scope of this work. Instead, we focus merely on scenarios with a stable leader, which is connected to at least a fast quorum of nodes.

\subsection{Mode Interoperability}
\label{sect:mode-interoperability}
The coexistence of multiple operating modes for the same slot within a single ballot necessitates a hybrid design that allows message processing from different protocol variants without compromising safety. To achieve this interoperability, every \texttt{Accept} and \texttt{Accepted} message is tagged with a corresponding \texttt{AcceptStatus}:
\begin{itemize}
\item \textbf{LeaderAccept (Regular Path):} Indicates a proposal issued by the leader via the standard Paxos protocol.
\item \textbf{FastAccept (Fast Path):} Indicates a proposal initiated directly by a follower attempting to reach a fast quorum.
\item \textbf{SlowAccept (Slow Path):} Indicates a remedial proposal issued by the leader to resolve a detected collision of proposals.
\end{itemize}

Append handling depends on the node’s local mode selection. In \textit{Fast Paxos} mode, the node broadcasts an \texttt{Accept} message with the \texttt{FastAccept} status directly to peers after assigning the slot with the smallest index that is still empty to the proposal. In \textit{Regular Paxos} mode, the proposal is forwarded to the current leader, which assigns the slot and broadcasts an \texttt{Accept} message with the \texttt{LeaderAccept} status.

A challenge in decentralized mode switching is a collision, where multiple nodes attempt to occupy the same log slot with different values via the fast path or the regular path. To maintain liveness, the leader maintains a record of all \texttt{Accepted} messages received from the cluster for every open slot. If the leader detects that no entry can be decided on due to a lack of responses or conflicting values for the same index, it triggers a resolution via the slow path. The concrete logic for the collision detection is described in Section \ref{sect:quorum-logic}. When having to use the slow path, the leader determines the correct entry to choose for this slot and broadcasts a new \texttt{Accept} message with the \texttt{SlowAccept} status.

The safety of the replicated log relies on strict rules regarding when a node is allowed to update its local state. \texttt{FastAccept} and \texttt{LeaderAccept} messages are treated as first-come, first-served. A follower is only allowed to accept these entries if the corresponding slot in its local log is currently empty. This rule is intended to prevent an uncoordinated follower from overwriting a value that may already have achieved a quorum elsewhere. In contrast, a message with \texttt{SlowAccept} status is treated as a command to resolve a conflict. Since this status is only issued by the leader after observing the cluster state, it is permitted to override any previously accepted value in a follower’s log. Under the assumption of a stable leader and fast-quorum connectivity, this hierarchy is intended to make the leader converge conflicting proposals toward a single value.

\subsection{Quorum Logic and Collision Detection}
\label{sect:quorum-logic}
This section details the deterministic logic utilized by the cluster leader to evaluate quorums, detect proposal collisions, and drive individual log slots to a decided state. None of the additional state maintained by the leader requires persistence to stable storage for recovery purposes even if applied in a fail-recovery model.

\begin{algorithm}[t]
\caption{Quorum Evaluation and Collision Resolution}
\label{alg:quorum_eval_collision_resolution}

\begin{algorithmic}[1]
\Procedure{ComputeProposeResult}{$proposals$}
\If{\textbf{not } majority quorum on $|proposals|$}
    \State \Return $\textsc{Pending}$
\EndIf
\State $(e^\star, leader, fast, slow) \gets$ entry in $proposals$ with maximum total votes
\If{majority quorum on $leader$ \textbf{or } \Statex \qquad\: fast quorum on $fast$ \textbf{or } \Statex \qquad\: majority quorum on $slow$}
    \State \Return $\textsc{Chosen}(e^\star)$
\EndIf
\If{\textbf{not } fast quorum on $|proposals|$}
    \State \Return $\textsc{Pending}$
\EndIf

\State $remaining \gets |nodes| - |proposals|$
\For{\textbf{each} $(e, leader, fast, slow)$ \textbf{in} vote counts of $proposals$}
    \If{fast quorum on remaining + fast \textbf{or } \Statex \qquad\qquad majority quorum on remaining + leader \textbf{or } \Statex \qquad\qquad slow > 0}
        \State \Return $\textsc{Collision}(e)$
    \EndIf
\EndFor
\State \Return $\textsc{Collision}(e^\star)$
\EndProcedure
\end{algorithmic}
\end{algorithm}

To evaluate the current state of an uncommitted log entry, the leader leverages Algorithm \ref{alg:quorum_eval_collision_resolution}. This algorithm operates as a pure function that takes the set of collected proposals and votes for a given slot and returns its discrete operational status: $\textsc{Pending}$, $\textsc{Collision}(entry)$ with $entry$ being a safe value to execute a slow path with or $\textsc{Chosen}(entry)$ where the $entry$ is free to be learned.

The evaluation begins by checking for immediate quorum satisfaction. A value is chosen once it reaches the quorum required by its \texttt{AcceptStatus}. This is a standard majority quorum for entries tagged with $\textsc{LeaderAccept}$ or $\textsc{SlowAccept}$, or a larger fast quorum for entries tagged with $\textsc{FastAccept}$. Because all these ways of acceptance require at least a majority of votes, it is enough to check the entry with the maximum total votes. Additionally, if less than a majority has voted, this also means that no decision could have been reached, making the slot $\textsc{Pending}$.

If no single entry has achieved its required quorum, the leader must determine whether a collision has occurred and select a value that cannot conflict with a potentially chosen value for the slow path under the made assumptions. Merely collecting a majority of total cluster responses is insufficient to safely trigger collision resolution in this mixed-mode environment. Consider, for instance, a cluster of five nodes, where a regular majority quorum consists of three and a fast quorum of four nodes. If the leader received three responses for a slot, with one being a $\textsc{LeaderAccept}$ of entry $A$ and two being $\textsc{FastAccept}$ messages of entry $B$, the outcome remains ambiguous, although a simple majority of responses has been gathered. With two nodes yet to respond, value $A$ could still theoretically achieve a majority quorum, while value $B$ could concurrently reach a fast quorum. Initiating a slow-path recovery at this stage risks overriding a value that might have achieved a quorum elsewhere in the network.

To avoid that, the leader must wait until a fast quorum of total responses has been collected for the slot. Then, it becomes mathematically impossible for more than one value to be able to reach its respective quorum using the remaining uncast votes. A proof of this is written out in Appendix \ref{seca:slow_path_resolution_safety_proof}.

After this threshold is met, the leader executes the final loop of Algorithm \ref{alg:quorum_eval_collision_resolution} to identify a valid candidate for the slow path. The leader computes the number of uncast votes ($remaining$) and checks if any entry can still mathematically achieve its required threshold. If an entry retains the potential to reach its quorum, it is selected as the safe value for the slow path. In cases where high contention prevents any entry from being able to reach a quorum, the system falls back to the entry with the highest current vote count.

\begin{algorithm}[t]
\caption{Leader Proposal Processing}
\label{alg:leader_proposal}

\begin{algorithmic}[1]

\Procedure{AddNewProposal}
{$pid, slotIdx, entry, status$}

\If{$slotIdx < decidedIdx$}
    \State \Return $\textsc{NoAction}$
\EndIf

\State Append $(pid, entry, status)$ to $\textit{acceptMeta}[slotIdx]$
\State $previous \gets \textit{slotResults}[slotIdx]$
\State $result \gets \Call{ComputeProposeResult}{acceptMeta[slotIdx]}$
\State $\textit{slotResults}[slotIdx] \gets result$

\If{$result = \textsc{Chosen}(\_)$ and $slotIdx = decidedIdx$}

    \State $newDecidedSuffix \gets [\ ]$

    \While{$\textit{slotResults}[decidedIdx] = \textsc{Chosen}(e)$}
        \State Append $(decidedIdx,e)$ to $newDecidedSuffix$
        \State Remove $\textit{slotResults}[decidedIdx]$
        \State Remove $\textit{acceptMeta}[decidedIdx]$
        \State $decidedIdx \gets decidedIdx+1$

    \EndWhile

    \State \Return $\textsc{DecidedAction}(newDecidedSuffix,decidedIdx)$
\ElsIf{$result = \textsc{Collision}(e)$ and $previous = \textsc{Pending}$}
    \State \Return $\textsc{SlowPathAction}(slotIdx,e)$
\Else
    \State \Return $\textsc{NoAction}$
\EndIf

\EndProcedure

\end{algorithmic}
\end{algorithm}

To translate the described quorum evaluation into concrete leader actions, the leader executes Algorithm \ref{alg:leader_proposal} upon receiving any accepted proposal, whether initiated by a follower or by itself. This mechanism serves as a stateful wrapper around the functional quorum computation.

The procedure begins with an initial safeguard step: any proposal targeting a log index prior to the currently contiguous decided sequence (denoted as $decidedIdx$) is immediately discarded as obsolete. Valid proposals are subsequently added to the internal metadata for the corresponding slot, ensuring an up-to-date record of all cast votes. The algorithm then invokes \texttt{ComputeProposeResult} and maps its returned state to one of three specific leader actions:
\begin{itemize}
    \item \textsc{DecidedAction}: This action is triggered when the slot achieves a \textsc{Chosen} state and perfectly aligns with the current $decidedIdx$. Upon this trigger, the algorithm sweeps forward through the internal metadata to identify all consecutively chosen slots. These contiguous entries form a single suffix that can now be permanently decided, subsequently advancing the cluster's $decidedIdx$.
    \item \textsc{SlowPathAction}: If the evaluation transitions the slot's state from \textsc{Pending} to $\textsc{Collision}(e)$, the leader emits a \textsc{SlowPathAction}. This directive instructs the leader to broadcast an \texttt{Accept} message with the \texttt{SlowAccept} status for value $e$, thereby resolving the detected collision according to the hierarchical rules established in Section \ref{sect:mode-interoperability}.
    \item \textsc{NoAction}: This fallback is returned either when the slot remains in a \textsc{Pending} state due to insufficient votes or when a collision has already been detected and acted upon in a previous iteration. The latter condition is required to prevent the emission of duplicate slow-path broadcasts for the same log index.
\end{itemize}

Entries, which have not been immediately decided or used for the slow path, can be directly retried for a different slot by the leader.

Assuming a stable leader and continued fast-quorum connectivity, the design is expected to preserve liveness during the accept phase. Compared to regular Sequence Paxos, if the cluster degrades to a simple majority, the leader might not be able to safely resolve collisions, effectively halting the log.

\section{Heuristic Score for Fast Path Success}
\label{sec:heuristic_score}
While the leader-side proposal processing and collision resolution described previously attempts to provide safety and liveness, the followers must individually choose the operating modes optimally for each request to achieve the best possible latency. Compared to regular Sequence Paxos, this means choosing to use the fast path when it is likely successful, avoiding the message delay for forwarding the request. Compared to Fast Sequence Paxos, this means choosing the safer forwarding option when a fast-path attempt is considered risky, since a collision  and its subsequent slow-path resolution and potential need for retrying introduce heavy latency penalties.

From the perspective of a follower, we can consider a fast path attempt successful only if its proposal achieves a fast quorum directly, without requiring a slow-path collision resolution. Conversely, a failure occurs whenever this optimal path is interrupted. A fast path attempt will fail if the target slot is claimed by a concurrent proposal by the leader through the regular path (majority quorum of $\textsc{LeaderAccept}$ messages), claimed by a different follower's concurrent fast path proposal (fast quorum of $\textsc{FastAccept}$ messages), or stalled entirely by a collision that forces the cluster into a slow-path recovery.

To dynamically determine the appropriate operating mode, we design a heuristic that condenses real-time metrics into a score estimating the probability of a fast path succeeding, serving as the foundation for the mode predictor. This is done empirically via network simulations.

We repeatedly simulate consensus networks spanning a broad range of operating conditions. Each simulation instantiates a cluster consisting of between four and eight nodes. The aggregate proposal rate is sampled logarithmically between 5 and 50,000 proposals per second, while the baseline one-way network latency is sampled logarithmically between 0.2 ms and 200 ms. The proportion of proposals initiated by the leader is sampled independently, with the remaining proposal load distributed randomly among the followers to expose different mixtures of regular- and fast-path traffic.

To introduce heterogeneous network conditions, every communication link is assigned an independent latency based on the sampled baseline latency together with randomized per-link variation. Individual message transmissions additionally experience randomized latency jitter, allowing each follower to observe a distinct network environment. Proposal generation and message delivery are simulated asynchronously using a discrete-event model.

The simulation duration is adjusted according to the aggregate proposal rate to ensure that each parameter configuration produces a sufficient number of proposal attempts while keeping the computational cost manageable. A total of 10,000 independent parameter configurations are simulated. After each simulation, every follower contributes one training sample consisting of locally observable runtime metrics together with the empirically measured fraction of proposals that completed successfully through the fast path. The parameter distributions are chosen to provide broad coverage of the operating space rather than to model a specific production workload. The resulting dataset is then used to investigate how different metrics influence fast-path success.

\subsection{Important Metrics}
To isolate the environmental variables that potentially impact fast-path outcomes, we define a set of system features tracked from the perspective of an individual follower. These metrics are divided into three categories driven by the structural trade-offs of the protocol: \textbf{Network Latency} captures time windows where proposals can be competed with; \textbf{Traffic and Proposal Rates} measure active, concurrent slot competition that could trigger a collision, and \textbf{System Scale} impacts the absolute quorum thresholds. The considered metrics are as follows:

\vspace{1em}
\noindent\textbf{Network Latency:}
\begin{itemize}
    \item \textit{Latency to Leader}: Baseline message delay to the designated leader.
    \item \textit{Latency to Majority Quorum}: The time required until a majority quorum can be reached with a message.
    \item \textit{Latency to Fast Quorum}: The time required until a fast quorum can be reached with a message.
    \item \textit{Maximum Latency}: Baseline message delay to the furthest node.
\end{itemize}

\noindent\textbf{Traffic and Proposal Rates:}
\begin{itemize}
    \item \textit{Leader Proposals/sec}: Volume of concurrent accept requests initiated by the leader. This is a measure about how many other requests take the regular path.
    \item \textit{Own Proposals/sec}: The individual request rate of the follower.
    \item \textit{Other Followers' Proposals/sec}: The aggregate concurrent request rate originating from all other followers. This is a measure about how many other requests take the fast path.
    \item \textit{Max Follower Proposals/sec}: The peak request rate observed from a competing follower.
\end{itemize}

\noindent\textbf{System Scale:}
\begin{itemize}
    \item \textit{Node Count}: Total number of active nodes operating within the  cluster.
\end{itemize}

    \includegraphics[width=\linewidth]{figures/all_features_importance.pdf}
    \caption{Feature importance for fast-path success measured by total information gain across the XGBoost model ensemble.} 
    \label{fig:all-features-importance}

To determine which of these metrics actually drive the system's behavior, we performed a feature importance analysis on the collected simulation data. An XGBoost regression model~\cite{Chen-XGBoost-2016} was trained using the established features to predict the empirical fraction of proposals that completed successfully through the fast path for an individual follower. The dataset was randomly partitioned into training (70\%), validation (15\%), and test (15\%) subsets. XGBoost models were trained on the training partition while monitoring the validation partition for early stopping to reduce overfitting. All reported evaluation metrics refer exclusively to the held-out test partition.

Using all the described metrics, the XGBoost model achieved a low \gls{RMSE} of $0.00372$ and a high \textit{Coefficient of Determination} ($R^2 = 0.97458$). This $R^2$ score indicates that the selected metrics account for approximately 97.5\% of the variance in fast-path success, validating that the input features successfully capture the underlying mechanics of the simulator.

The relative impact of each metric was quantified using the \textit{Information Gain} of the underlying decision trees. This was selected because it measures the reduction in prediction error contributed by each feature over all tree splits in the ensemble. The result is illustrated in Figure~\ref{fig:all-features-importance}.

XGBoost is deliberately employed as an exploratory analysis tool because it provides robust feature importance estimates while modeling highly nonlinear feature interactions. To minimize system overhead, however, the resulting score function should be simpler and efficient to compute, requiring as little runtime metric tracking as possible. For this purpose, the goal is to first reduce the feature space without losing much performance. From the original feature importance plot, we observe that latency to the fast quorum contributed the largest information gain. If we remove all other latency features and repeat the XGBoost training procedure, we achieve a \gls{RMSE} of $0.00631$ and $R^2$ score of $0.95689$, which demonstrates that the model retains most of its predictive accuracy despite using a significantly smaller feature set. Figure~\ref{fig:one-latency-features-importance} shows the resulting feature importance.

With these three established metrics, we now try to build a lightweight analytical approximation as an efficient score function for the final runtime predictor.

\subsection{Score Function}
To explore how the three remaining metrics interact, we can look at the time a proposal spends in flight. The \textit{Latency to Fast Quorum} can be thought of as a window where a fast-path proposal is vulnerable to competition. During this time, requests from both the leader and other followers could potentially disrupt the fast path. Therefore, summing these two rates and multiplying by the latency gives a dimensionless value that could track the number of competing proposals issued during that window. This combination provides a plausible starting point for a well-defined score function, which is also underlined by the fact that an XGBoost model just on this metric produces a \gls{RMSE} of $0.00806$ an $R^2$ score of $0.94495$. This is very close to the results achieved using the original features separately.

When visualizing the "competing proposals" against the fast-path success rate in log-space (as done in Figure~\ref{fig:score-function}), a clear pattern emerges. The data exhibits a distinct sigmoid-like shape, with the success rate remaining near one for low values before dropping sharply and flattening out at zero. 
\begin{figure*}[t]
    \includegraphics[width=\linewidth]{figures/score_function.pdf}
    \caption{Observed fast-path success rate versus the expected number of competing proposals. The red line highlights the analytical heuristic score used for prediction.}
    \label{fig:score-function}
\end{figure*}

To approximate this relationship, we fit a sigmoid function using the "competing proposals", $x$, which is the product of the fast quorum latency and the combined proposal rate. The model is formulated as follows:
$$\hat{\pi}(x) = \frac{1}{1 + e^{k(\ln(x) - \ln(x_0))}}$$
A curve fit yields a steepness factor of around $k \approx \frac{5}{4}$ and a parameter $x_0 \approx 0.5$, which marks the inflection point where the predicted success rate drops to $0.5$. The latter is consistent with intuition, as when there is a $50\%$ chance of a competing proposal, then it is imaginable that there is roughly a $50\%$ chance of our fast-path attempt not being involved in a conflict.

Inserting these values and transforming the equation leads to the final heuristic model, as visualized in Figure \ref{fig:score-function}, in the following form:
$$\vec{x} = \begin{bmatrix} x_1 \\ x_2 \end{bmatrix} = \begin{bmatrix} \text{Fast Quorum Latency (s)} \\ \text{Incoming Accept Messages/s} \end{bmatrix}$$
$$\pi(\vec{x}) = \frac{1}{1 + (2 \cdot x_1 \cdot x_2)^{\frac{5}{4}}}$$

With this function, we achieve a \gls{RMSE} of $0.00817$ and an $R^2$ score of $0.94422$ on the test data. This small trade-off in accuracy is acceptable to have a negligible computation and an interpretable score. A summary comparing the performance metrics of each model iteration against the original feature set is provided in Table~\ref{tab:model-performance-comparison}. The function can now serve as the heuristic notion of uncertainty, as needed for \gls{CRC}, around the mode prediction. An evaluation of its usability is presented in Section \ref{sec:score_function_validity}.

\section{Risk-Controlled Mode Prediction}
\label{sec:risk-controlled_mode_prediction}
To bound the risk of failed fast-path attempts, the system incorporates the heuristic function into a risk-controlled prediction layer, outlined in this section. This framework wraps the scoring model to bound the empirical rate of fast-path failures relative to a user-specified risk level $\alpha$ in the long run. This failure rate is measured relative to the total number of append attempts initiated by the node, rather than only the subset of proposals where the fast-path was actively selected.

\subsection{Risk Specification}
To formulate the mode selection as a risk-control problem, the system's outcomes and penalties must be strictly defined. We establish this formulation using three primary components: the label space, the loss function, and the user-defined risk level.

First, we define the operational label space of a proposal attempt as $\mathcal{Y} = \{\textsc{Success}, \textsc{NoSuccess}\}$. A $\textsc{Success}$ indicates that a fast-path proposal from the perspective of the proposing follower achieves a fast quorum directly under the current network conditions. Conversely, a $\textsc{NoSuccess}$ means that the attempt fails.

To bound the failure rate of fast paths, which is the risk we are trying to control, we have to penalize the false positives, where a fast-path is chosen and ends up being unsuccessful. If we fall back to the conservative/regular path whenever the \texttt{NoSuccess} label is included in the prediction set, the loss can be defined as such: The loss should be $1$ whenever the true outcome is \texttt{NoSuccess}, but the prediction set fails to include \texttt{NoSuccess} (meaning the system confidently, but incorrectly, predicted a fast-path success) and $0$ otherwise. This loss is mapped using Table \ref{tab:loss-matrix}.

\begin{table}[t]
\centering
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{lcccc}
& \multicolumn{4}{c}{\textbf{Prediction Set}} \\
\cmidrule(l){2-5}
\textbf{True Label} & $\emptyset$ & $\{Success\}$ & $\{NoSuccess\}$ & $\{Success, NoSuccess\}$ \\
\midrule
\textbf{Success}   & 0 & 0 & 0 & 0 \\
\textbf{NoSuccess} & \textbf{1} & \textbf{1} & 0 & 0 \\
\bottomrule

The design does not punish conservative predictions where the fast-path would have succeeded but the system safely defaulted to the regular path. The reason for this choice is that such a punishment simply does not fit into a loss function that has to satisfy the monotonicity properties relevant to provide the guarantees of \gls{CRC}, as outlined in Section \ref{sect:conformal_risk_control}.

To mathematically evaluate this loss against our target failure rate, we must formally define the output of the prediction layer based on the heuristic established in Section \ref{sec:heuristic_score}. Let $\vec{x} \in \mathcal{X}$ denote the vector of real-time network features, and let $\pi(\vec{x})$ be the heuristic score representing the estimated probability of a fast-path success. We define a generalized scoring function $s(\vec{x}, y)$ for the label space $\mathcal{Y}$, where:
\begin{alignat*}{2}
&s(\vec{x}, \textsc{Success}) &&= \pi(\vec{x})\\
&s(\vec{x}, \textsc{NoSuccess}) &&= 1 - \pi(\vec{x})
\end{alignat*}
We can then define the predictor as a set-valued function $\mathcal{C}_\lambda: \mathcal{\vec{x}} \rightarrow 2^{\mathcal{Y}}$ controlled by a calibration parameter $\lambda \in [0, 1]$. For a given proposal attempt, the prediction set is constructed by including any label whose score meets or exceeds the threshold $1 - \lambda$:
$$\mathcal{C}_\lambda(\vec{x}) = \{ y \in \mathcal{Y} \mid s(\vec{x}, y) \ge 1 - \lambda \}$$
This construction guarantees monotonicity with respect to $\lambda$. A maximally conservative parameter ($\lambda = 1$) lowers the inclusion threshold to $0$, yielding the complete label space $\mathcal{C}_1(X) = \{\textsc{Success}, \textsc{NoSuccess}\}$, which guarantees a safe fallback to the regular path. Conversely, as $\lambda$ approaches $0$, the threshold tightens, and the prediction set shrinks to only include labels with a high degree of heuristic certainty. 

Finally, the framework bounds the risk using a user-specified risk level $\alpha \in (0, 1)$, which dictates the target failure rate. If we had an exchangeable calibration set, the standard \gls{CRC} procedure would provide the following guarantee for a new test point:
$$\mathbb{E}(\mathcal{L}(\mathcal{C}_{\widehat\lambda}(X_{test}), Y_{test})) \le \alpha$$
Since real-life workloads are unlikely to be exchangeable, however, we instead use the rolling risk-control procedure (as defined in Section \ref{sect:adaptive_conformal_inference}), which gives us the following for a stream of decision problems:
$$\lim_{T \to \infty} \frac{1}{T} \sum_{t=1}^T \mathcal{L}(\mathcal{C}_{\lambda_t}(X_t), Y_t) \le \alpha$$
Here, the converging value is bounded by $\alpha$ instead of being equal to it, as outlined previously. The reason is that in a setup where the fast-path always succeeds, the failure rate (and therefore the risk) is zero. Formally, our loss function does not satisfy the property that it has to produce a value higher than $\alpha$ when provided an empty prediction set since $\mathcal{L}(\emptyset, Success) = 0 < \alpha$.

\subsection{Decision Layer}
To execute runtime mode switching, each follower monitors local environment metrics. The fast quorum latency can be tracked continuously via a sliding window of recent message round-trip times to a fast quorum of peers, while the incoming proposal rate is calculated by recording the timestamps of arriving \texttt{Accept} messages from other nodes within a moving time window.

\begin{algorithm}[t]
    \caption{Conformal Mode Prediction}
    \label{alg:conformal_mode_prediction}
    \begin{algorithmic}[1]
        \Procedure{GetPredictionSet}{$features, \lambda$}
            \State $scores \gets \textsc{Model}(features)$
            \State $predictionSet \gets [\ ]$
            \For{\textbf{each} $(label, score)$ \textbf{in} $scores$}
                \If{$score \ge 1.0 - \lambda$}
                    \State Append $label$ to $predictionSet$
                \EndIf
            \EndFor
            \State \Return $predictionSet$
        \EndProcedure
        \vspace{0.5em}
        \Procedure{GetNewMode}{$features$}
            \State $labels \gets \Call{GetPredictionSet}{features, \widehat{\lambda}}$
            \If{$\textsc{NoSuccess} \in labels$}
                \State \Return $\textsc{RegularPaxos}$
            \Else
                \State \Return $\textsc{FastPaxos}$
            \EndIf
        \EndProcedure
    \end{algorithmic}
\end{algorithm}

For every proposal attempt, the decision layer follows Algorithm \ref{alg:conformal_mode_prediction}. First, the tracked metrics are fed into the heuristic function to obtain probability scores for both outcomes in the label space $\mathcal{Y}$. Next, a prediction set is constructed by including any label whose assigned score satisfies the threshold condition bounded by the conformal parameter $\widehat{\lambda}$. Intuitively, a threshold of $\widehat{\lambda} = 1$ always returns the full label set, forcing a maximally conservative posture, whereas a threshold of $\widehat{\lambda} = 0$ collapses the selection down to an empty set.

Finally, the contents of the prediction set are directly translated into an operational mode for the proposal. If the set contains the \texttt{NoSuccess} label, the node falls back to Regular Paxos, forwarding proposals to the leader. Conversely, if \texttt{NoSuccess} is absent from the prediction set, the node switches to FastPaxos mode and initiates fast-path broadcasts instead.

\subsection{Calibration Strategy}
To calibrate the prediction layer, nodes require ground-truth data indicating whether a fast-path attempt would have succeeded under the current network conditions. To gather this data without impacting safety on the active log, the system can employ a parallel data-gathering mechanism using shadow proposals.

Whenever a node opts for the regular path and forwards a proposal to the leader, it can simultaneously broadcast a shadow proposal tagged with a \texttt{TestAccept} status to all peers. Receiving followers treat \texttt{TestAccept} messages passively: if the target log slot is currently empty, the follower acknowledges the message by sending an \texttt{Accepted} response back to the original proposer, but it strictly does not write the entry to its local replicated log.

The original proposer accumulates these responses to determine the simulated outcome. If a \texttt{TestAccept} gathers a fast quorum of acknowledgments, the hypothetical fast-path attempt is deemed successful, and a \textsc{Success} label is recorded alongside the corresponding feature state. Conversely, if the actual log slot is committed by the leader via a \texttt{Decide} without the fast quorum being formed, meaning many nodes have ignored this shadow proposal and the attempt is considered failed, it records a \textsc{NoSuccess} label. While this mechanism might occasionally underestimate fast-path viability, for instance, if the forwarded regular proposal is processed exceptionally fast or if an acknowledgment packet is dropped, it provides a sufficiently accurate proxy metric under stable network conditions.

Actual calibration can then happen two different ways: offline and online. In an offline calibration phase, the node collects a batch of shadow proposal outcomes to form a static dataset. The system then computes an optimal initial parameter, $\widehat{\lambda}$ using the standard \gls{CRC} approach, by employing a binary search algorithm to find the exact root where the empirical risk over the calibration set matches the significance level $\alpha$. While this offline batch calibration does not provide formal theoretical guarantees for non-exchangeable future data, it can establish a sound baseline.

An online calibration phase utilizes the rolling risk control mechanism to incrementally update the threshold after each decision problem $t$. Using a defined learning rate $\gamma$, the parameter is adjusted based on the observed loss:
$$\widehat{\lambda}_{t} \leftarrow \widehat{\lambda}_t + \gamma \left( \mathcal{L}(\mathcal{C}_{\hat{\lambda}_t}(X_t), Y_t) - \alpha \right)$$
This continuous adjustment bounds the failure rate and provides the long-term risk guarantees outlined previously.

Notably, the system does not need to issue shadow proposals during this online phase with our current loss function. Because of its definition, it evaluates to exactly zero whenever the prediction set contains the \textsc{NoSuccess} label, which forces the node to take the regular path. The true label of what \textit{would} have happened on the fast-path becomes mathematically irrelevant for the parameter update. The loss can only be non-zero when the system chooses the fast-path and subsequently fails. As a result, the online risk-control loop can operate without the network overhead of shadow proposals.
