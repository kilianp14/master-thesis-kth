\section{Experimental Setup}
The evaluation prototype is implemented in the Rust programming language, building directly upon a trimmed-down fork of the original OmniPaxos codebase. To cleanly isolate the protocol variables associated with decentralized mode switching, several production-level features of OmniPaxos were omitted. The log is managed entirely via an in-memory storage layer, which enforces a fail-stop failure model where nodes do not recover from persistent disk state. Log compaction mechanisms, including truncation and snapshotting, are excluded. Because the evaluation assumes a stable leader and continuous fast-quorum connectivity, a fully safe log synchronization phase at the conclusion of the prepare phase was omitted. Additionally, request batching is disabled to process proposals individually, ensuring that performance evaluation isolates fine-grained end-to-end latency rather than aggregate throughput.

Building upon this baseline, the consensus layer incorporates the required protocol interoperability and modification rules. Both Accept and Accepted messages are extended to include an explicit AcceptStatus field. Followers are equipped with the logic necessary to bypass the leader and broadcast proposals directly to peers via the fast path. To handle the resulting mixed-mode logs, the leader's volatile state is modified to execute the tracking and deterministic collision-detection logic defined in Algorithm \ref{alg:quorum_eval_collision_resolution} and Algorithm \ref{alg:leader_proposal}. Follower-side update semantics are enforced to maintain safety: followers reject standard FastAccept and LeaderAccept messages if the target log index is already occupied, but they permit SlowAccept commands from the leader to override existing entries during collision resolution.

When we operate in adaptive mode, the system implements dedicated tracking mechanisms for network features and performance labels. To estimate the fast-quorum latency, the \gls{BLE} layer extends its standard heartbeat messages with a microsecond timestamp; upon receiving a reply, the round-trip time is divided by two to compute individual one-way network latencies. Concurrently, the sequence Paxos layer tracks a running count of incoming Accept requests received within a sliding one-second window to estimate the proposal rate of other cluster nodes. Ground-truth labels are gathered using a dual approach. During the offline calibration phase, followers issue passive shadow proposals tagged with a TestAccept status alongside their forwarded regular requests to measure hypothetical fast-path viability without committing data. In the active operational phase, the system dispenses with shadow proposals and gathers labels implicitly by analyzing the final AcceptStatus of a node's own completed proposals once they are decided, where a resolved FastAccept signifies a fast-path success.These features and labels are processed by a prediction and calibration engine implemented as an isolated Conformal Mode Predictor module, which is invoked by the consensus layer during every append attempt. The module evaluates the non-linear heuristic model and executes the decision framework outlined in Algorithm \ref{alg:conformal_mode_prediction}. The calibration parameter ($\widehat{\lambda}$) is managed across two phases. In the offline calibration phase, the system executes a binary root-finding algorithm over a pre-collected batch dataset of shadow proposals to establish the initial baseline threshold. During runtime operations, an online calibration routine continuously updates the threshold via rolling updates, applying a gradient-descent step based on the real-time empirical loss to enforce the long-term risk bounds.

\subsection{State Machine Application}
For the experiments, we used a linearizable, in-memory key-value store as the application-level replicated state machine. State transitions and queries are driven by three basic operations: inserting a key-value pair, deleting a key, or retrieving a value based on a key. To guarantee strict linearizability and prevent stale data, both read and write operations are appended to the consensus log. As the consensus engine commits these entries, the server executes the commands sequentially once they are decided.

Client requests are encapsulated into a standardized command structure that includes a unique command identifier and a coordinator node identifier. Upon receiving a request, the coordinator node appends this command to the consensus log. After the log entry is committed and executed sequentially by the state machine, the node matching the recorded coordinator identifier handles routing the final execution outcome back to the originating client.
